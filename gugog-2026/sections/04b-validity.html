Semantic validity

Can semantic and graphical expressivity be combined within a single system, or are users better served by clearly distinct tools? Systems that validate every operation necessarily constrain the arrangement space, and systems that maximize arrangement coverage necessarily leave validity to the user. Characterizing which of these trade-offs are principled and which are merely incidental to current implementations is an important open research problem.

Cynthia Huang & Matthew Kay, Semantic Validity vs. Graphical Arrangement in Visualization Grammars, GUGOG 2026

Bartonicek et al. [2] examine the widespread usage of stacked bar charts over dodged bar charts in interactive graphics, and offer an explanation for this preference based in Gestalt principles. They then proceed to argue that only statistics with monoidal structure (e.g. counts, sums, products) should be displayed as stacked bars with linked highlighting of single group subsets (parts of whole), based on the algebraic properties of summary functions. The authors offer this result, and a similar one for multi-group selection, as a preliminary contribution towards complete algebraic foundations for ‘coherent and well-behaved’ interactive graphics. They invoke a more constrained notion of expressivity that is conditional on statistical and mathematical validity. In fact, Bartonicek et al. const data = [
  { month: "Jun", city: "Boston", temp: 21, usd: 120 },
  { month: "Jun", city: "Chicago", temp: 22, usd: 95 },
  { month: "Jul", city: "Boston", temp: 24, usd: 135 },
  ...
];

chart(data, {
  schema: {
    temp: Unit("°C"),
    usd: Unit("USD", { traits: [Trait.summable()] }),

If there is spare time: to stack °C you either declare the unit summable, which is a deliberate claim about your data, or you stack the means. The only thing it takes away is stacking numbers whose sums mean nothing.

The code is the same as on the step before. Only the output changed.

The error is not typed in: the slide runs this spec live and prints the message GoFish throws. It is checkSummable's error in src/ast/measure.ts (origin/main): "A size channel sums the column "temp", in the unit "°C", which cannot be summed: it has no CanSum. If its amounts add up (money, counts, lengths), declare it with Unit("°C", { traits: [Trait.summable()] }). If they do not (temperatures, prices, rates), average them instead, e.g. field("temp").mean()."

Fair framing:

  • This is the idea Cynthia and Matt call Error Friction (their section 4 design principles and section 6.3): invalid specifications are made costly to reach, while valid ones stay fluid.
  • It blocks the hazard they name in section 2 ("Motivating Contributions"): if linked selection were added without validity checks, "the grammar would silently permit combinations, such as stacking of group means". A .mean() result is not summable, so stack refuses it.

Fair framing:

  • Limits, said plainly: this is one operator and one property. Bartonicek et al.'s actual setting, linked highlighting in interactive graphics, is not addressed here. "I haven't found a principled tradeoff yet" is not "there isn't one."
  • Their paper calls the two kinds of contribution "distinct and complementary" (section 5.1). CanSum is offered in that spirit, as one mechanism that bears on their question.

For Q&A or the panel, not the slides: the same type information covers the unit aspect ratio case in Jason Brunson's GUGOG paper, where biplots and point clouds need one unit on x to equal one unit on y. GoFish tracks at the type level whether two axes have the same type, and if they do, it uses the same scale for both by default.
